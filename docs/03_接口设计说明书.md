# 03 接口设计说明书（Civ5 Agent Command）

> [!IMPORTANT]
> 本文档定义系统各模块之间的**完整接口契约（签名、参数、返回值与核心 JSON Schema 字段）**。后续多会话并行开发时，各模块必须严格遵循本文档定义的字段命名与类型，以确保无需二次重构即可直接联调。

---

## 一、 接口 1：游戏 Lua $\leftrightarrow$ 外部 MCP Server 的 SQLite IPC 协议

* **数据库文件**：`ModUserData/Civ5AgentBridge-1.db`（引擎内置 SQLite `3.7.17`）
* **承载表**：原生 `SimpleValues(Name TEXT PRIMARY KEY, Value VARIANT)`；当载荷字节数超过 `3000` 时按 **1-based** 槽位 `<key>#chunk_1 .. <key>#chunk_N` 自动分片，主槽位仅写入短标记 `"__CHUNKED__:<len>"`（规避定长缓冲区截断风险），最后写入 `rpc_request_req_id` / `rpc_response_req_id` 作为原子发布屏障。

### 1.1 键值槽位定义

| Key (`Name`) | 写入方 | 读取方 | 用途与内容格式 |
| :--- | :---: | :---: | :--- |
| `bridge_heartbeat` | Lua Mod | MCP Server | JSON：`{ "turn": 45, "active_player": 0, "status": "IDLE" \| "TURN_SYNCED", "last_req_id": 101, "clock_ms": 12345 }` |
| `turn_overview_auto` | Lua Mod | MCP Server | 每当 `Events.ActivePlayerTurnStart` 触发或点击同步按钮时，Lua 自动写入当前回合初始态势 JSON |
| `rpc_request` | MCP Server | Lua Mod | 外部下发的请求 JSON（超 3KB 时分片存储于 `rpc_request#chunk_1..N`）：`{ "req_id": 101, "method": "...", "params": {...} }` |
| `rpc_request_req_id` | MCP Server | Lua Mod | 整数字符串（如 `"101"`）：请求载荷及分片全部落盘后最后写入的**请求发布游标**，Lua 帧轮询仅轻量读取此键判断是否有新请求 |
| `rpc_response` | Lua Mod | MCP Server | Lua 处理并完成动作结算后写回的响应 JSON（超 3KB 时分片存储于 `rpc_response#chunk_1..N`）：`{ "req_id": 101, "ok": true, "data": {...}, "error": null }` |
| `rpc_response_req_id` | Lua Mod | MCP Server | 整数字符串（如 `"101"`）：响应载荷及分片全部写完后最后写入的**响应完成游标**，MCP Server 轮询匹配此键后安全拼接载荷 |
| `<key>#chunk_count` / `<key>#chunk_1..N` | 双向 | 双向 | 分片元数据与 **1-based** 分片内容槽位（`chunk_count == "0"` 表示未分片直接读 `<key>`；`> 0` 时按 `1..N` 顺序拼接） |

### 1.2 Lua IPC 方法表 (`rpc_request.method`)

| `method` 名称 | 输入 `params` | 输出 `data` 核心字段 | 用途说明 |
| :--- | :--- | :--- | :--- |
| `ping` | `{ "echo": "str" }` | `{ "pong": "str", "turn": int }` | 连通性与 RTT 延迟检测 |
| `get_turn_overview` | `{}` | 见 `§2.1 TurnOverviewDTO` | 提取当前玩家可见全局态势（单位、城市、可见敌情、资源） |
| `get_unit_context` | `{ "unit_id": int, "radius": int }` | 见 `§2.2 UnitTacticalContextDTO` | 提取指定单位周边 $R$ 格地形/驻军及该单位当前**合法候选动作列表** |
| `execute_unit_action` | `{ "unit_id": int, "action_type": str, "target_x": int, "target_y": int }` | 见 `§2.3 ActionExecutionResultDTO` | 驱动单位执行单步动作，并在结算后返回最新状态与**增量揭盲敌情 (`delta_enemies`)** |

## 二、 接口 2：Civ5 MCP Server 暴露的工具集 (MCP Tools)

模块 2（`civ5_mcp_server.py`，基于本机官方 `mcp 2.3.0` `MCPServer` 实现，支持 `stdio` 与 `streamable-http` 传输及 `--mock-snapshot` / `--live-db` / `CIV5_BRIDGE_MODE` 切换）向外暴露以下 5 个标准 MCP Tool，供模块 4（编排引擎）直接调用，或通过 `agy mcp add` 挂载至 `agy` CLI：
> [!NOTE]
> `LIVE` 模式下 `Civ5AgentBridgeCore.lua` 原生采集 `strategic_resources`、`is_fortified`、`current_production`、`turns_left`、`visible_enemy_cities`、`newly_revealed_tiles_count` 与 `target_enemy_after`（保障 `LEVEL 1` 残敌补刀与攻城战真值准确）；MCP Server 适配层同时保留 `setdefault` 规范化守卫，确保任何边缘空值下 `LIVE` 与 `MOCK` 返回契约 100% 同构。

### 2.1 `get_turn_overview`
* **签名**：`async def get_turn_overview() -> dict`
* **用途**：供**顾问 (Tier 1)** 与 **参谋长 (Tier 2)** 获取当前回合全局可见态势。
* **返回结构 (`TurnOverviewDTO`)**：
  * `turn_number` (`int`)：当前回合号
  * `player_civ` (`str`)：玩家文明名称
  * `yields` (`dict`)：`{ "gold": int, "gold_per_turn": int, "science_per_turn": int, "happiness": int, "strategic_resources": dict[str, int] }`
  * `our_units` (`list[UnitSummaryDTO]`)：每个元素含 `{ "unit_id": int, "name": str, "unit_type": str, "domain": "LAND"|"AIR"|"SEA", "x": int, "y": int, "hp": int, "max_hp": int, "moves_left": float, "max_moves": float, "combat_str": int, "ranged_str": int, "range": int, "is_fortified": bool, "can_act": bool }`
  * `visible_enemies` (`list[EnemyUnitDTO]`)：仅包含当前视野可见（`IsVisible == true`）的敌方/蛮族单位，字段含 `{ "enemy_id": str, "owner_name": str, "is_barbarian": bool, "unit_type": str, "x": int, "y": int, "hp": int, "combat_str": int, "ranged_str": int }`
  * `our_cities` (`list[CitySummaryDTO]`)：`{ "city_id": int, "name": str, "x": int, "y": int, "pop": int, "hp": int, "current_production": str, "turns_left": int }`
  * `visible_enemy_cities` (`list[EnemyCityDTO]`)：已探索/可见的敌方或城邦城市列表（含是否处于迷雾标记 `in_fog: bool`）

### 2.2 `get_unit_context_and_candidates`
* **签名**：`async def get_unit_context_and_candidates(unit_id: int, radius: int = 3) -> dict`
* **用途**：供**执行者 (Tier 3)** 与 **Jev** 获取指定单位的局部六边形战场网格及引擎校验过的合法候选动作。
* **返回结构 (`UnitTacticalContextDTO`)**：
  * `unit` (`UnitSummaryDTO`)：当前单位最新状态
  * `surrounding_tiles` (`list[TileDTO]`)：半径 `radius` 内所有已探索地块，每个元素含 `{ "x": int, "y": int, "distance": int, "visibility": "VISIBLE"|"REVEALED_FOG", "terrain": str, "feature": str|null, "is_hills": bool, "has_river": bool, "improvement": str|null, "friendly_unit_id": int|null, "enemy_unit": EnemyUnitDTO|null, "city": dict|null }`
  * `candidate_actions` (`list[CandidateActionDTO]`)：由 Lua 调用引擎接口枚举出的合法原子动作（含相邻未探索黑雾格的探路 `MOVE_STEP`、攻城器械远程前架设 `SETUP_FOR_RANGED` 以及空军全射程 `AIR_STRIKE`），每个元素含：
    * `action_id` (`str`)：唯一候选编号（如 `"ACT_01"`）
    * `action_type` (`Literal["MOVE_STEP", "MELEE_ATTACK", "RANGE_ATTACK", "AIR_STRIKE", "SETUP_FOR_RANGED", "FORTIFY", "HEAL", "SKIP_TURN"]`)
    * `target_x` (`int`), `target_y` (`int`)：目标坐标
    * `estimated_cost_moves` (`float`)：预计消耗移动力
    * `combat_preview` (`dict | null`)：若为攻击动作，提供 `{ "target_enemy_type": str, "target_hp_before": int, "terrain_modifier_note": str }`
    * `note` (`str`)：动作辅助说明（如 `"Explore adjacent unrevealed hex"` 或 `"AirRaidLegacyUnits strike"`）

### 2.3 `execute_unit_step`
* **签名**：`async def execute_unit_step(unit_id: int, action_type: str, target_x: int, target_y: int) -> dict`
* **用途**：供**执行者 (Tier 3)** 在游戏内执行单步动作，并立刻拿回增量视野用于 **Jev** 中断判别。
* **返回结构 (`ActionExecutionResultDTO`)**：
  * `executed` (`bool`)：指令是否成功执行
  * `error_reason` (`str | null`)：失败原因（如移动力不足、目标非法）
  * `unit_after` (`UnitSummaryDTO | null`)：动作结算后的单位状态（若阵亡则为 `null` 且 `unit_died: true`）
  * `delta_observation` (`DeltaObservationDTO`)：
    * `newly_revealed_tiles_count` (`int`)：本步新揭开的地块数
    * `newly_spotted_enemies` (`list[EnemyUnitDTO]`)：**本步动作前不可见、动作后新暴露在视野内的敌方单位列表（触发自下而上反馈的核心依据）**
    * `target_enemy_after` (`EnemyUnitDTO | null`)：若为攻击动作，受击敌军结算后的残余血量状态（若被消灭则 `enemy_killed: true`）

### 2.4 `save_turn_snapshot` & `load_turn_snapshot`
* **签名**：
  * `async def save_turn_snapshot(tag: str) -> str`
  * `async def load_turn_snapshot(snapshot_path: str) -> dict`
* **用途**：将当前回合完整状态导出至 `data/snapshots/`（返回保存后的绝对路径字符串，兼容 `LIVE` 录制与 `MOCK` 无损断点），或将 MCP Server 热切换至离线 `MOCK` 模式并加载指定快照（返回 `{ "loaded": bool, "runtime_mode": "MOCK", "snapshot_path": str, "overview": TurnOverviewDTO }`）。

## 三、 接口 3：多模型统一网关接口 (`LLMGateway`)

模块 3 为上层编排器提供统一的模型调用协议，屏蔽 `agy` CLI 与 `GLM API` 的差异。

### 3.1 `LLMProvider.generate`
* **签名**：
  ```python
  async def generate(
      role_tier: Literal["TIER1_ADVISOR", "TIER2_CHIEF", "TIER3_EXECUTOR"],
      prompt: str,
      system_prompt: str,
      response_model: type[TModel] | None = None,
      conversation_id: str | None = None,
      effort: Literal["low", "medium"] = "low",
      enable_thinking: bool = False,
      on_stream_event: Callable[[StreamEvent], Awaitable[None]] | None = None,
  ) -> LLMResponse[TModel]
  ```
* **用途与后端规范**：
  * 当路由至 **`AgyCliProvider`** 时：在独立空工作目录 `cwd` 下组装 `agy.exe -p <prompt> --output-format stream-json --effort <effort> --disable-slash-commands`（按需附加 `--conversation <id>`；挂载 MCP 时附加 `--dangerously-skip-permissions`；单轮 JSON 提取校验未过时自动附加 `--json-schema <temp_schema_path>` 重试），逐行读取 NDJSON 并触发 `on_stream_event` 推送增量。
  * 当路由至 **`GlmApiProvider`** 时：默认直连智谱 Coding Plan 专属端点 `https://open.bigmodel.cn/api/coding/paas/v4/chat/completions`（从环境变量 `ZHIPU_API_KEY` 读取密钥，可选代理 `http://127.0.0.1:7897`），请求 `glm-5.4 / 5.3 / 5.3-flash`，按 `enable_thinking` 显式传入 `"thinking": {"type": "enabled" | "disabled"}`，并在指定 `response_model` 时完成 Pydantic v2 强校验。
* **返回结构 (`LLMResponse`)**：
  * `text` (`str`)：完整回复文本
  * `structured_data` (`dict | None`)：通过 `json_schema` 解析并校验后的字典
  * `thinking_log` (`str`)：模型思考过程摘要
  * `conversation_id` (`str | None`)：供同一回合内多轮对话复用的会话 ID
  * `backend_used` (`str`)：实际执行的后端标识（如 `"agy:gemini-hydrogen"` 或 `"zhipu:glm-5.4"`）
  * `latency_ms` (`int`)：端到端耗时

## 四、 接口 4：三层指挥链公文流转与中断上报 Schema

以下 4 个核心数据结构是**顾问 (Tier 1) $\leftrightarrow$ 参谋长 (Tier 2) $\leftrightarrow$ 执行者 (Tier 3)** 之间传递的标准化“电子公文”契约：

### 4.1 跨回合交接材料 (`HandoffDocument`)
保存在 `data/handoffs/turn_{N}_handoff.json`，由上一回合生成、本回合初交给**顾问**与**参谋长**，并在本回合末根据实际执行结果修订：
* `from_turn` (`int`)：交接来源回合号
* `long_term_strategy` (`str`)：跨回合总体战略意图（例如：“北线依托丘陵河岸防守反击，攒钱升级复合弓手后再反推”）
* `active_operations` (`list[dict]`)：跨回合持续进行中的作战/建设计划 `{ "op_name": str, "assigned_unit_ids": list[int], "status": str, "next_turn_focus": str }`
* `unresolved_threats` (`list[str]`)：上一回合遗留的威胁或迷雾未知风险点
* `last_turn_execution_summary` (`str`)：上一回合实际完成情况与偏差说明

### 4.2 本回合工作文书 (`WorkDirective`)
由**顾问 (Tier 1)** 拟定草案，经玩家在 TUI 中交流确认后签发生效，下发给**参谋长 (Tier 2)**：
* `turn_number` (`int`)：当前回合号
* `commander_intent_summary` (`str`)：玩家与顾问达成一致的本回合总体方针
* `theater_directives` (`list[TheaterDirectiveDTO]`)：分战区/分方向的工作指示：
  * `theater_id` (`str`)：如 `"NORTH_FRONT"`
  * `priority` (`Literal["CRITICAL", "HIGH", "NORMAL"]`)
  * `involved_unit_ids` (`list[int]`)：划归该方向调度的我方单位 ID 列表
  * `directive_text` (`str`)：具体工作要求（如“远程集火消灭(14,20)蛮族步兵，残血矛兵后撤过河休整”）
* `redline_constraints` (`list[str]`)：**执行红线约束**（一旦违反或面临违反风险，必须触发 `LEVEL 2` 中断上报玩家，例如：“任何我方单位死亡风险不得超过阈值”、“侦察兵遇敌立即停止前进”）

### 4.3 参谋长任务部署单 (`TaskPackage`)
由**参谋长 (Tier 2)** 根据《本回合工作文书》拆解并按执行先后顺序排定，下发给**执行者 (Tier 3)**：
* `task_id` (`str`)：如 `"TASK_T45_01"`
* `execution_order` (`int`)：执行优先级序号（解决 1UPT 让路与先远程消耗、后近战收割的顺序问题）
* `executor_type` (`Literal["COMBAT_UNIT_EXECUTOR", "SCOUT_EXECUTOR", "AIR_STRIKE_EXECUTOR"]`)
* `unit_ids` (`list[int]`)：本任务包操控的单位 ID（通常为 1 个主战单位或 1 支协同小队）
* `tactical_posture` (`Literal["ADVANCE", "FOCUS_FIRE", "HOLD_DEFEND", "RETREAT_HEAL", "RECON_CAUTIOUS"]`)：供 **Jev 分类器** 使用的标准战术姿态标签
* `target_area` (`dict`)：`{ "target_x": int, "target_y": int, "target_enemy_id": str | null }`
* `step_instruction` (`str`)：参谋长给执行者的明确战术指令说明
* `abort_on_new_enemy_count` (`int`)：当单步揭开迷雾新发现敌军数量 $\ge$ 该阈值时，强制触发上报

### 4.4 下级主动上报单 (`EscalationReport`)
当**执行者 + Jev** 在执行中遇到新情报或阻碍时构造此对象，打破“自上而下”流程，逆向抛回**参谋长 (Tier 2)** 或**顾问 (Tier 1)**：
* `escalation_id` (`str`)
* `level` (`Literal[1, 2]`)：
  * `1` = **战术级上报（交参谋长处理）**：如目标已被前序友军消灭、目标格被友军占领需改道、攻击后敌军残血需调集邻近单位补刀；
  * `2` = **战略级警报（经参谋长直达顾问并弹窗请示玩家）**：如拨开迷雾发现敌方主力军团、继续执行将触犯《工作文书》红线约束。
* `source_task_id` (`str`)：触发上报的任务包 ID
* `trigger_unit_id` (`int`)：触发上报的单位 ID
* `trigger_reason_tag` (`Literal["FOG_AMBUSH_DETECTED", "PATH_BLOCKED_1UPT", "TARGET_SURVIVED_LOW_HP", "REDLINE_RISK_HIGH", "ACTION_INVALID"]`)
* `delta_observation` (`DeltaObservationDTO`)：触发上报时的最新视野增量数据
* `situation_brief` (`str`)：由执行层生成的简明前线军情汇报
* `options_for_superior` (`list[str]`)：供上级（参谋长或玩家）拍板的备选处置方案（如 `["A. 立即就地驻扎转入防御", "B. 按原计划强行推进", "C. 撤回河岸后方"]`）

### 4.5 参谋长上报处置响应单 (`ChiefEscalationDecisionOutput`)
经 `EXP-05` 验证固化，当参谋长（Tier 2）收到 `EscalationReport` 时返回此结构化门控对象，用于精确分流两条逆向中断分支：
* `can_resolve_tactically` (`bool`)：
  * `true` = 属于局部战术协同范畴（对应 `LEVEL 1`），参谋长直接在内部通过 `replanned_tasks` 更新任务队列并跳回 `EXECUTING`，**不打扰顾问与玩家**；
  * `false` = 触及《本回合工作文书》红线或超出战术微调权限（对应 `LEVEL 2`），状态机继续退回 `ESCALATED_TO_ADVISOR` 请示玩家。
* `chief_assessment` (`str`)：参谋部对异常态势的战术/战略威胁研判附言。
* `replanned_tasks` (`list[TaskPackage]`)：当 `can_resolve_tactically == true` 时，针对当前仍有剩余移动力（`can_act == true`）的单位重新编排的后续任务包列表。

### 4.6 各层级大模型结构化输出顶层包装契约 (`LLM Output Envelopes`)
经 `EXP-05` 真实大模型联调固化，顾问（Tier 1）与参谋长（Tier 2）调用 `LLMGateway` 时统一使用以下 3 个顶层 Pydantic 包装模型（连同 `§4.5 ChiefEscalationDecisionOutput` 共 4 个顶层输出模型）：
* **`AdvisorProposalOutput`**（顾问在回合初拟稿或响应 `LEVEL 2` 拍板修订时输出）：
  * `advisor_brief_to_player` (`str`)：面向玩家的简明战略汇报
  * `work_directive` (`WorkDirective`)：《本回合工作文书》草案/修订稿
  * `next_handoff_draft` (`HandoffDocument`)：《下轮交接材料》初稿
* **`AdvisorEscalationAlertOutput`**（顾问接收 `LEVEL 2` 战略警报后向玩家呈报请示时输出）：
  * `urgent_brief_to_player` (`str`)：前线突发险情与红线冲突简报
  * `recommended_option_index` (`int`)：顾问推荐方案下标（`0-based`）
  * `options_for_player` (`list[str]`)：供玩家拍板的备选战略方案列表（至少 2 项）
* **`ChiefDispatchOutput`**（参谋长拆解已批准《工作文书》时输出）：
  * `dispatch_summary` (`str`)：参谋部拆单与协同顺序说明
  * `tasks` (`list[TaskPackage]`)：有序任务部署单列表（至少 1 项）

## 五、 接口 5：Jev 决策分类器与轨迹采集接口 (`JevService`)

模块 5 严格定位为**判别式状态分类器**，对外提供以下 3 个接口：

### 5.1 候选动作战术评级 (`evaluate_candidate_actions`)
* **签名**：
  ```python
  async def evaluate_candidate_actions(
      unit_context: UnitTacticalContextDTO,
      task_package: TaskPackage,
  ) -> list[JevScoredActionDTO]
  ```
* **输入**：单位局部战场上下文（含所有合法 `candidate_actions`）+ 参谋长下发的 `TaskPackage`（含 `tactical_posture` 与 `target_area`）。
* **输出 (`list[JevScoredActionDTO]`)**：按推荐度降序排列，每项含：
  * `action_id` (`str`)：对应 `CandidateActionDTO.action_id`
  * `label` (`Literal["OPTIMAL", "ACCEPTABLE", "HIGH_RISK", "VIOLATES_ORDER"]`)：四分类判别结果
  * `confidence` (`float`)：$0.0 \sim 1.0$ 分类置信度/打分
  * `rationale_short` (`str`)：简短判别依据（展示在 TUI 右栏监控流中）

### 5.2 动作后增量态势中断判别 (`evaluate_step_escalation`)
* **签名**：
  ```python
  async def evaluate_step_escalation(
      before_context: UnitTacticalContextDTO,
      exec_result: ActionExecutionResultDTO,
      task_package: TaskPackage,
      redlines: list[str],
  ) -> JevEscalationDecisionDTO
  ```
* **输出 (`JevEscalationDecisionDTO`)**：
  * `escalation_level` (`Literal[0, 1, 2]`)：`0`=继续执行本单位剩余移动力或下一任务；`1`=中断并上报参谋长；`2`=中断并上报顾问请示玩家。
  * `reason_tag` (`str`)：分类原因标签
  * `confidence` (`float`)

### 5.3 训练轨迹落盘与人工修正接口 (`record_jev_trajectory` / `record_jev_trajectory_async`)
* **签名**：
  ```python
  def record_jev_trajectory(
      sample_type: Literal["ACTION_CLASSIFICATION", "ESCALATION_CLASSIFICATION"],
      state_features: dict,
      jev_prediction: dict,
      final_adopted_label: str | int,
      was_overridden_by_human_or_superior: bool,
      meta: dict | None = None,
  ) -> str

  async def record_jev_trajectory_async(...) -> str  # 内部经 asyncio.Lock + asyncio.to_thread 调用同步落盘
  ```
* **用途**：将每次判别的归一化定长特征与最终被采纳的正确标签写入 `data/jev_trajectories.jsonl`（经 `EXP-07` 固化为 `schema_version="jev_traj_v1"`：`ACTION_CLASSIFICATION` 固定 18 维数值/枚举特征列，`ESCALATION_CLASSIFICATION` 固定 14 维增量特征列，异步调用侧经 `record_jev_trajectory_async` 非阻塞追加落盘），供后续上传 Colab Pro 进行 Jev 模型零清洗微调。

## 六、 接口 6：编排引擎 $\leftrightarrow$ Textual TUI 控制台事件总线接口

模块 4（编排引擎）与模块 6（Textual TUI）通过异步 `@dataclass(slots=True)` 事件对象通信，完全解耦 UI 渲染与 Agent 逻辑（完整对齐 `EXP-07` `events.py` 实证签名）：

### 6.1 编排引擎推向 TUI 的消息 (`OrchestratorToUIMessage`)
* `TurnStateUpdatedEvent(overview: TurnOverviewDTO, phase: SessionPhaseEnum, runtime_mode: Literal["MOCK", "LIVE"])`：刷新顶部状态栏与左栏战场态势/部队列表。
* `AgentStreamChunkEvent(tier: Literal["TIER1_ADVISOR", "TIER2_CHIEF", "TIER3_EXECUTOR"], chunk_type: Literal["THINKING", "TEXT"], content: str)`：实时流式追加到中栏（顾问对话）或右栏（参谋长/执行者日志）。
* `DirectiveDraftReadyEvent(directive_draft: WorkDirective, handoff_draft: HandoffDocument, advisor_brief: str = "")`：在中栏渲染《本回合工作文书》与《下轮交接材料》审批卡片，点亮【批准】与【修改】按钮。
* `TaskQueueUpdatedEvent(tasks: list[TaskPackage], active_task_id: str | None = None, note: str = "")`：刷新右栏参谋长任务包队列与当前执行高亮。
* `StepExecutedEvent(unit_id: int, scored_actions: list[JevScoredActionDTO], result: ActionExecutionResultDTO, escalation_level: Literal[0, 1, 2] = 0, escalation_reason: str = "NOMINAL_CONTINUE", trajectory_count: int = 0)`：在右栏打印单步 Jev 分类结果、游戏执行反馈与已落盘样本计数。
* `EscalationAlertEvent(report: EscalationReport, advisor_urgent_brief: str = "", recommended_option_index: int = 0)`：当发生 `LEVEL 2` 战略警报时，在中栏弹出高亮军情警报框并等待玩家决断。
* `TurnCompletedEvent(turn_number: int, final_handoff: HandoffDocument, handoff_path: str, trajectory_path: str, trajectory_count: int)`：整回合落盘收尾回执。
* `SystemNoticeEvent(level: Literal["INFO", "WARN", "ERROR"], message: str)`：模型热切换、快照录制或紧急中止等轻量状态通知。

### 6.2 TUI 发向编排引擎的控制指令 (`UIToOrchestratorCommand`)
* `SyncTurnFromGameCommand(auto_start_advisor: bool = True)`：主动从游戏 SQLite 或离线快照拉取最新回合状态并启动第一部分（顾问）。
* `PlayerChatToAdvisorCommand(message: str)`：玩家向顾问发送自然语言指令或修改意见。
* `ApproveWorkDirectiveCommand(edited_directive: WorkDirective | None = None)`：玩家确认批准《本回合工作文书》（`None` 表示直接批准当前草案），启动第二部分（参谋长拆单）与第三部分（执行环）。
* `ResolveEscalationCommand(escalation_id: str, chosen_option: str, custom_instruction: str | None = None, override_jev_label: bool = True)`：玩家对突发军情做出决断（同时触发 `record_jev_trajectory_async` 记录人类修正样本）。
* `SwitchTierModelCommand(tier: Literal["TIER1_ADVISOR", "TIER2_CHIEF", "TIER3_EXECUTOR"], provider_and_model: str)`：动态切换某层级的底层模型（如将参谋长从 `agy` 切为 `zhipu:glm-5.4`）。
* `RecordSnapshotCommand(tag: str = "tui_manual")` & `AbortExecutionCommand(reason: str = "玩家手动紧急中止")`：对应左栏「录制快照」与中栏「紧急中止执行」按钮控制动作。
